# Журнал работы с ИИ

Использовала Codex на базе GPT-6. Исходный контекст — PDF тестового задания
Junior Python / FastAPI. Дальше уточняла архитектуру, запуск, проверки и доставку
образа. Код, команды и проверки выполнял ассистент; я задавала требования и
возвращалась с уточнениями. Ниже — технически сформулированный пересказ реальных
запросов и результатов, а не дословные цитаты. Детали реализации, предложенные
ассистентом, описаны отдельно от моих исходных требований.

## Три ключевых запроса

1. Реализовать API платежей по приложенному PDF: сохранить контракт эндпоинтов,
   целочисленные суммы в копейках, промокод, график рассрочки, идемпотентность и
   допустимые переходы статусов. Основание для этих требований — само задание.
2. Использовать PostgreSQL, вынести бизнес-обработку в отдельный worker, передавать
   команды и ответы через Redis и собрать сервисы в Docker. Код должен оставаться
   понятным, чтобы я могла разобраться в нём перед собеседованием.
3. Добавить CI со всеми тестами, затем CD; проверить реальные запуски, объяснить
   пропущенную публикацию и слить ветки перед сдачей. Подготовить README для запуска
   с Docker и без него, requirements и историю работы с ИИ.

## Как шла работа

### 1. Передала задание и уточнила объём

Сначала передала PDF и попросила сделать проект. Дважды останавливала работу,
чтобы уточнить требования до продолжения реализации. Источником бизнес-правил
оставался PDF: четыре эндпоинта, три тарифа, скидка 10%, рассрочка на 3/6/12 месяцев,
HTTP-коды и формат ответов. Мои дополнения касались PostgreSQL, Redis, Docker и CI.

### 2. Уточнила границы сервисов и роль Redis

Просила отдельный обработчик алгоритма и передачу данных через Redis в обе стороны.
Первоначальное описание контейнеров было неоднозначным; итоговая схема — `api`,
`worker`, `redis`, `postgres`. API валидирует запрос и возвращает HTTP-ответ,
worker выполняет бизнес-логику и работает с ORM. Для данных достаточно одной БД;
Swagger используется для просмотра и ручной проверки API.

Ассистент реализовал Redis Streams для команд и отдельный ключ ответа для каждого
`request_id`. API ждёт результат в рамках исходного HTTP-запроса, поэтому клиент
сразу получает предусмотренные заданием `201`, `200`, `404` или `409`.

### 3. Попросила читаемый код и CI со всеми тестами

В одном из уточнений отдельно попросила понятный код, автоматические тесты и этот
журнал. В реализации расчёты вынесены в `domain.py`, входные модели — в `schemas.py`,
транзакционная обработка — в `service.py`, транспорт — в `broker.py` и `worker.py`.
Скидка считается целочисленно, остаток рассрочки распределяется в первые платежи.

Для защиты от одновременных запросов ассистент использовал уникальное ограничение
на `Idempotency-Key` и блокировку строки при смене статуса. Изменение платежа и
результат команды сохраняются одной транзакцией PostgreSQL. Повторная доставка
команды после сбоя worker возвращает сохранённый результат. Эти механизмы —
решения реализации, а не дословные требования из моего первоначального сообщения.

CI проверяет Ruff, форматирование, pytest с настоящими PostgreSQL и Redis,
затем запуск четырёх контейнеров и доступность API по HTTP. Помимо обязательных
сценариев добавлены проверки конкурирующих запросов, повторной доставки и сбоев.

### 4. Уточнила готовность приложения и выбор ОС

Спросила, можно ли считать приложение рабочим после успешного CI, можно ли добавить
CD и почему контейнер приложения не основан на Ubuntu. Ассистент объяснил границы
проверок: зелёный CI подтверждает выполненные сценарии; развёртывание на отдельном
сервере требует собственной проверки.

Для приложения выбран официальный `python:3.12-slim` на Debian; GitHub Actions
использует `ubuntu-latest`. ОС контейнера и ОС сервера могут различаться. Это
объяснение добавлено в README вместе с описанием доставки образа.

### 5. Попросила requirements и оценку по критериям задания

Попросила добавить установку зависимостей через pip и обосновать соответствие
критериям оценки. `requirements.txt` и `requirements-dev.txt` экспортированы из
`uv.lock` с фиксированными версиями. Ассистент проверил установку в отдельном
виртуальном окружении, импорт приложения, зависимости и тесты.

Обоснование опиралось на конкретные сценарии: точность денежных расчётов, отсутствие
дублей, запрет неверных переходов, содержание тестов и воспроизводимый запуск.
100 баллов проверяющий ещё не выставлял; работающий код также нужно уметь объяснить
и изменить на созвоне.

### 6. Попросила запуск без Docker

Попросила описать обычный локальный запуск, в том числе для тестов. В README
добавлены установка PostgreSQL и Redis, создание пользователя и двух баз,
виртуальное окружение и запуск API и worker в отдельных терминалах.

Отдельно описаны тестовые переменные окружения, база `kvitto_test` и различия портов
локальных служб и тестовых контейнеров. Для быстрых проверок расчётов есть команда
`pytest tests/test_domain.py -q`, которой PostgreSQL и Redis не требуются.
Установка системных служб на чистой Ubuntu в этой сессии не выполнялась.

### 7. Разобрала настройки публикации образа

Показала фрагмент workflow с `GITHUB_REPOSITORY`, `GITHUB_SHA` и `GITHUB_TOKEN`
и спросила, нужно ли дополнять его вручную. Ассистент объяснил, что значения
предоставляет GitHub Actions, а токену публикации нужно право `packages: write`.
Образ получает два тега: SHA коммита и `latest`.

Затем спросила, почему CD не работает. Публикация настроена после успешного CI
только для события `push` в `main`. Доставка образа в GHCR реализована;
автоматическое обновление сервера в этот workflow не входит.

### 8. Попросила исправить CI и объяснить его использование

Попросила поднять CI и оформить историю работы человеческим языком. При проверке
GitHub Actions обнаружилась ошибка форматирования в `app/service.py`: пробелы
на пустой строке. Ассистент исправил её через Ruff и отправил новый коммит.
Повтор старого запуска использовал бы старый код, поэтому требовался новый push.

В README добавлена инструкция: где открыть запуск, как найти упавший шаг,
исправить форматирование и отправить изменения. После исправления CI в `develop`
прошёл, включая интеграционные тесты и запуск приложения.

### 9. Уточнила значение пропущенного этапа на скриншоте

Прислала скриншот с зелёным `checks` и серым `Publish tested application image`.
Причина оказалась в условии ветки: запуск был из `develop`, поэтому публикация
была пропущена. Ошибки публикации в этом запуске не было — этап не выполнялся.

### 10. Попросила слить ветки и проверить готовность к сдаче

Ассистент обновил сведения о ветках, сохранил журнал, выполнил слияние `develop`
в `main` через `--ff-only` и отправил обе ветки в GitHub. Они сошлись на коммите
`021856b`. Для этого коммита проверены логи Actions: **88 тестов прошли**, Ruff и
форматирование успешны, четыре контейнера запустились, запрос к API выполнен.

В `main` успешно прошла и публикация образа `ghcr.io/zaringa/test_to_kvitto`
с тегами SHA и `latest`. Результат доступен в
[запуске CI/CD](https://github.com/zaringa/test_to_kvitto/actions/runs/37536494413).
Обязательные требования PDF сверены с проектом; деплой на сервер заданием
не требуется. Alembic и список платежей с фильтрами остались необязательными бонусами.

### 11. Попросила подробнее оформить журнал

В последнем уточнении попросила раскрыть шаги и сформулировать запросы более
технически. Журнал дополнен контекстом, результатами и причинами исправлений.
Пересказ отделён от дословной переписки и от решений, которые предложил ассистент.
После изменения Markdown проверено отсутствие ошибок пробелов через `git diff --check`.

## Какие предложения ИИ пришлось исправить

- Сначала Redis предлагалось использовать только для фоновых событий. Это расходилось
  с моим уточнением о передаче всех команд и ответов через него; схему изменили.
- Первоначальная зависимость SQLAlchemy не включала `greenlet`. Тестовый запуск
  выявил `ImportError`; после замены на `sqlalchemy[asyncio]` тесты прошли.
- Локальные изменения форматирования нужно было довести до нового коммита:
  GitHub CI обнаружил пробелы на пустой строке и остановил проверку Ruff.
  Ошибка исправлена, новый запуск завершился успешно.

## Что проверено и как продолжать работу

Проверки выполнял ассистент: Ruff, форматирование, actionlint, 88 тестовых сценариев
с настоящими PostgreSQL и Redis, установка через pip и HTTP-запросы к приложению
в четырёх контейнерах. Тесты проверяют суммы, содержимое ответов и состояние БД,
в том числе при конкурентных запросах и повторной обработке команд.

Команды запуска и проверки находятся в [README](README.md). Для следующей доработки
удобно передать ассистенту конкретный сценарий, ожидаемый результат, ограничения
из задания и фактический лог ошибки. После изменения нужно проверить результат
и разобраться в соответствующем участке кода перед собеседованием.
